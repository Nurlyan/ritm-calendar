# Ритм · Совместный календарь

Статический адаптивный сайт для GitHub Pages. Без сборки и без ChatGPT-входа. Публичные файлы интерфейса не содержат личных записей. Supabase обеспечивает вход по email, базу, разграничение прав и подписку на изменения.

## Текущее состояние

Пока `config.js` пуст, включён **локальный режим**: данные хранятся только в localStorage этого браузера. Это не защищённый общий доступ и не межустройственная синхронизация. В интерфейсе есть заметное предупреждение. Облако заработает после шагов ниже. Данные локального режима автоматически в облако не переносятся.

## Публикация на GitHub Pages

1. Создайте публичный репозиторий `ritm-calendar`.
2. Загрузите содержимое этой папки в корень репозитория, включая `.github/workflows/pages.yml` и `.nojekyll`.
3. В Settings → Pages → Build and deployment выберите **GitHub Actions**.
4. Запустите workflow `Publish GitHub Pages` либо отправьте новый commit в `main`.
5. Дождитесь зелёного результата Deploy. Адрес страницы указан в результатах workflow. Не считайте публикацию завершённой до успешного Deploy.

## Подключение Supabase

1. Создайте проект в Supabase. Выберите тариф и регион в своём аккаунте; условия бесплатного плана проверяйте при создании. Пароль базы храните у себя.
2. Откройте SQL Editor и выполните `supabase.sql` **один раз** в новом проекте.
3. В Authentication → Users создайте владельца и зрителя с реальными email. Не публикуйте пароли и ссылки входа. Создание пользователей и принятие условий сервиса выполняет владелец аккаунта.
4. Скопируйте UUID этих пользователей. Выполните две закомментированные команды внизу SQL-файла с настоящими UUID. Вторая команда выдаёт девушке только просмотр. Не назначайте ей `owner_id`.
5. В Authentication → URL Configuration установите Site URL и Redirect URL на точный адрес GitHub Pages, включая `/ritm-calendar/`. Включите вход по email/magic link. Проверьте ограничения отправки email своего проекта; при необходимости подключите свой SMTP. Приложение не регистрирует произвольных новых пользователей (`shouldCreateUser: false`).
6. Заполните `config.js`: `supabaseUrl` — URL проекта; `supabaseKey` — **публичный** publishable/anon key; `calendarId` — UUID календаря из результата SQL. Эти три значения можно включить в публичный сайт. **Никогда не помещайте service_role, secret key или пароль в репозиторий.**
7. Опубликуйте изменение. На странице «Доступ и связь» войдите с email владельца, затем с email девушки на другом устройстве.
8. Выполните проверки ниже. Пока они не пройдены, не считайте роли и синхронизацию проверенными в рабочей среде.

## Приёмка облака

- Владелец меняет занятие, девушка получает новый план без перезагрузки. Подписка Realtime дополняется сверкой каждые 20 секунд.
- Девушка не видит дневник, не может изменить таблицу calendars через API; SQL RLS запрещает UPDATE зрителю. Запрос sleep_entries от её аккаунта возвращает только её собственные записи (их нет), без записей владельца. INSERT сна разрешён только пользователю, владеющему календарём.
- Анонимный посетитель видит форму входа и не получает общие данные из базы.
- Два владельческих устройства одновременно меняют план: второе получает конфликт версии, без перезаписи свежего состояния.
- После отключения интернета облачная запись завершается ошибкой, успех не показывается. Нет очереди офлайн-изменений: повторите после восстановления связи.
- Прямой запрос API с нарушением сна, пересечением блоков или сдвинутым вторничным созвоном отвергается триггером БД.

## Правила календаря

Подъём всегда 09:30. Занятия находятся внутри 09:30–00:30. Отход ко сну всегда 00:30–00:45, засыпание до 01:00 — отдельная цель. Созвон во вторник 20:00–21:20 неизменен. Начало работы по умолчанию 10:00, его можно сдвинуть на 10:20.

Переносы сохраняют длительность следующих блоков, находят для них следующие свободные окна и обходят созвон. Непоместившиеся занятия **показываются до подтверждения**, затем сохраняются в список переносов с возможностью выбрать новый день. Ничто не переносится в сон. Добавление занятия внутрь текущего блока сокращает текущий блок до нового начала; это видно в предварительном плане. Для изменения более раннего занятия редактируйте его напрямую.

Отметки факта всегда хранят реальные дату и время. В сегодняшнем дне предлагается перестроить остаток дня. Если перестроение невозможно, можно сохранить только факт, оставив план прежним. Закреплённый созвон допускает фактические отметки, сохраняя целевой интервал.

Сценарий среды/четверга меняет расписания целиком; дни с фактическими отметками так менять нельзя. Базовый спорт: Пн/Чт/Пт/Сб. Вело — ручная альтернатива, автоматической проверки погоды нет.

Основной календарь и статус работают в Москве (UTC+3). Поля и список дневника сна отображаются во времени устройства; данные сохраняются как ISO UTC. Анализ — средняя длительность между записанными отходом ко сну и подъёмом и среднее субъективное качество. Это не измерение фактического сна и не медицинская диагностика.

История хранит последние 200 изменений календаря и доступна обоим пользователям. Дневник в историю не включается. JSON-экспорт владельца содержит его сон: храните резервную копию лично. Локальный режим не имеет защищённой роли зрителя.

## Локальная проверка

Node.js: `npm test`. Для просмотра: `python -m http.server 4173 --bind 127.0.0.1`, затем откройте `http://127.0.0.1:4173/`. Не открывайте index.html через file://: браузеру нужны ES-модули по HTTP. Зависимостей для локального режима нет. Облачный SDK загружается с esm.sh при подключённой конфигурации; шрифт загружается из Google Fonts, при недоступности используется системный.
